## 맥락

리뷰, 가게, 댓글을 관계형으로 저장해야 한다.
배포는 가볍게 하고 싶고, 로컬 개발과 테스트는 별도 설치 없이 바로 돌아가야 한다.

## 결정

우리는 `local`·`test` 프로필에서 H2 인메모리 DB(PostgreSQL 호환 모드)를, `prod` 프로필에서 Neon 서버리스 PostgreSQL을 쓴다.
스키마는 Flyway로 관리하고, 두 DB에서 모두 실행되는 SQL을 공통 마이그레이션으로 둔다.

## 검토한 대안

### 대안 1: 모든 환경에서 PostgreSQL (Docker 또는 Testcontainers)
- 장점: 운영과 같은 DB로 테스트해 DB 차이로 인한 오류가 없다.
- 단점: 로컬에 Docker가 필요하고 테스트 시작이 느리다.
- 채택하지 않은 이유: 1시간 개발 목표에서 설정 부담이 크다.

### 대안 2: 운영도 Render PostgreSQL 사용
- 장점: 배포 플랫폼 하나로 관리할 수 있다.
- 단점: 무료 DB에 사용 기간 제한이 있다.
- 채택하지 않은 이유: Neon은 무료로 오래 쓸 수 있고, 개발용 브랜치와 시점 복구를 제공한다.

### 대안 3: MySQL
- 장점: 널리 쓰인다.
- 단점: 부분 일치 검색 인덱스(`pg_trgm`) 같은 PostgreSQL 기능을 쓸 수 없다.
- 채택하지 않은 이유: 검색 요구사항에 PostgreSQL이 더 맞다.

## 결과

- 좋은 점: 로컬과 테스트가 설치 없이 바로 돌아가고, 운영 DB는 관리 부담이 적다.
- 감수하는 점: H2와 PostgreSQL의 차이로 테스트는 통과해도 운영에서 실패할 수 있다. Neon은 유휴 후 첫 요청이 느리다.
- 후속 작업: PostgreSQL 전용 SQL은 `{vendor}` 경로로 분리하고, 배포 전에 Neon 개발 브랜치에서 마이그레이션과 검색을 확인한다. JDBC URL 변환 방법을 배포 문서에 적는다.
