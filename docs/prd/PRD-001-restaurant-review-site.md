## 1. 배경 및 문제

맛집 정보는 블로그, SNS, 지도 앱에 흩어져 있고 광고성 글이 섞여 있어 믿을 만한 후기를 찾기 어렵다.
가입 없이 누구나 가볍게 후기를 남기고, 가게별 평가를 한곳에서 검색해 볼 수 있는 사이트를 만든다.
검색 엔진에 잘 노출되고 첫 화면이 빠르게 뜨도록 모든 페이지를 서버 사이드 렌더링(SSR)으로 제공한다.

## 2. 목표와 성공 지표

- 목표: 로그인 없이 리뷰를 작성·검색·댓글로 소통할 수 있는 맛집 리뷰 서비스의 첫 버전(MVP)을 제공한다.
- 성공 지표
  - 방문자가 리뷰 작성 페이지에 들어와서 등록까지 완료하는 비율 60% 이상
  - 검색 결과 페이지 서버 응답 시간 p95 500ms 이내 (리뷰 10만 건 기준)
  - 공개 후 한 달 동안 리뷰 1건당 평균 댓글 1개 이상
  - 리뷰 상세 페이지가 검색 엔진에 색인됨 (JavaScript 없이 본문이 HTML에 포함)

## 3. 대상 사용자

- **리뷰 작성자**: 다녀온 식당의 경험을 가입 절차 없이 빠르게 남기고 싶은 사람
- **리뷰 탐색자**: 지역이나 음식 종류로 맛집을 찾고 다른 사람의 평가를 비교하고 싶은 사람
- **댓글 참여자**: 리뷰에 질문하거나 자신의 경험을 덧붙이고 싶은 사람

## 4. 사용자 스토리

- 작성자로서, 다녀온 가게의 경험을 공유하기 위해 가게 정보와 별점, 후기를 등록하고 싶다.
- 작성자로서, 잘못 쓴 내용을 고치기 위해 등록할 때 정한 비밀번호로 리뷰를 수정·삭제하고 싶다.
- 탐색자로서, 원하는 맛집을 찾기 위해 키워드로 검색하고 지역·카테고리로 좁혀 보고 싶다.
- 탐색자로서, 가게를 고르기 위해 가게별 평균 별점과 리뷰 목록을 보고 싶다.
- 댓글 참여자로서, 리뷰 내용을 더 알아보기 위해 로그인 없이 댓글을 달고 싶다.

## 5. 범위

### 포함
- 익명(닉네임 + 비밀번호) 리뷰 작성·조회·수정·삭제
- 리뷰 항목: 제목, 본문, 별점(1~5), 가게 정보(이름, 주소, 지역, 음식 카테고리)
- 가게별 상세 페이지와 평균 별점
- 키워드 검색 + 지역·카테고리 필터 + 최신순/별점순 정렬, 페이지네이션
- 리뷰에 대한 익명 댓글 작성·조회·삭제
- Thymeleaf 기반 SSR 페이지

### 제외
- 회원가입·로그인·소셜 로그인: 첫 버전은 진입 장벽을 낮추는 데 집중한다.
- 사진 첨부: 저장소·용량·유해 이미지 관리 부담이 커서 다음 버전에서 검토한다.
- 태그, 가격대: 필수 요구가 아니어서 제외한다.
- 지도·위치 기반 검색: 외부 지도 API 연동이 필요해 이후 단계로 미룬다.
- 대댓글, 좋아요, 신고, 관리자 페이지: 이후 단계에서 검토한다.
- REST API와 SPA 프론트엔드: 모든 화면은 SSR로만 제공한다.

## 6. 기능 요구사항

### FR-1: 리뷰 작성 (Must)

사용자는 로그인 없이 닉네임, 비밀번호, 가게 정보, 별점, 제목, 본문을 입력해 리뷰를 등록한다.
가게 정보는 기존 가게를 검색해 선택하거나, 없으면 새 가게를 입력한다.

- 닉네임 2~20자, 비밀번호 4~20자, 제목 1~100자, 본문 10~5,000자, 별점은 1~5 정수로 모두 필수다.
- 비밀번호는 복호화할 수 없는 해시로만 저장한다.

**인수 조건**
- Given 모든 필수 항목을 올바르게 입력했을 때, When 등록 버튼을 누르면, Then 리뷰가 저장되고 해당 리뷰 상세 페이지로 이동한다.
- Given 필수 항목이 비었거나 길이 조건을 어겼을 때, When 등록 버튼을 누르면, Then 입력값이 유지된 채 항목별 오류 메시지가 표시된다.
- Given 등록이 완료된 뒤, When 브라우저에서 새로고침하면, Then 리뷰가 중복 등록되지 않는다.

### FR-2: 가게 정보 관리 (Must)

리뷰는 반드시 하나의 가게에 속한다.
가게는 이름, 주소, 지역, 음식 카테고리를 가진다.

- 카테고리는 고정 목록에서 고른다: 한식, 중식, 일식, 양식, 아시안, 분식, 카페·디저트, 주점, 기타.
- 지역은 목록에서 고르지 않고 사용자가 직접 입력한다 (1~30자, 예: "서울 종로구"). 앞뒤 공백은 제거하고 저장한다.
- 입력 폼에는 "시·도 시·군·구" 형식으로 쓰도록 예시(placeholder)를 보여 준다.
- 이름과 주소가 모두 같은 가게는 중복 등록되지 않는다.

**인수 조건**
- Given 이름과 주소가 같은 가게가 이미 있을 때, When 새 가게로 리뷰를 등록하면, Then 새 가게를 만들지 않고 기존 가게에 리뷰가 연결된다.
- Given 가게 이름 일부를 입력했을 때, When 가게 찾기를 실행하면, Then 이름에 해당 문자열이 포함된 기존 가게 목록이 표시된다.

### FR-3: 리뷰 조회 (Must)

- 목록 페이지는 리뷰를 한 페이지에 20개씩 최신순으로 보여 준다. 각 항목에는 제목, 가게 이름, 별점, 닉네임, 작성일, 댓글 수를 표시한다.
- 상세 페이지는 리뷰 전체 내용, 가게 정보(가게 상세 페이지 링크 포함), 댓글 목록을 보여 준다.

**인수 조건**
- Given 리뷰가 25개 있을 때, When 목록 1페이지에 접속하면, Then 최신 리뷰 20개와 2페이지로 가는 링크가 표시된다.
- Given 존재하지 않거나 삭제된 리뷰 ID로, When 상세 페이지에 접속하면, Then 404 페이지가 표시된다.
- Given JavaScript를 끈 브라우저로, When 상세 페이지에 접속하면, Then 리뷰 본문과 댓글이 모두 보인다.

### FR-4: 리뷰 수정·삭제 (Must)

작성 때 입력한 비밀번호가 일치해야 수정하거나 삭제할 수 있다.

**인수 조건**
- Given 올바른 비밀번호를 입력했을 때, When 수정을 저장하면, Then 변경 내용이 반영되고 상세 페이지에 "수정됨" 표시와 수정 시각이 보인다.
- Given 틀린 비밀번호를 입력했을 때, When 수정 또는 삭제를 요청하면, Then 요청이 거부되고 "비밀번호가 일치하지 않습니다" 메시지가 표시된다.
- Given 댓글이 달린 리뷰를, When 삭제하면, Then 리뷰와 그 댓글이 DB에서 완전히 지워지고, 목록·검색·가게 페이지 어디에도 "삭제된 리뷰" 같은 흔적이 남지 않는다.
- Given 비밀번호를 여러 번 틀렸을 때, When 다시 요청하면, Then 잠금 없이 계속 비밀번호를 대조한다.

### FR-5: 가게 상세 페이지 (Should)

가게 이름, 주소, 지역, 카테고리, 평균 별점(소수점 첫째 자리), 리뷰 수, 해당 가게의 리뷰 목록을 보여 준다.

**인수 조건**
- Given 별점 4, 5, 5인 리뷰 3개가 있는 가게에, When 상세 페이지에 접속하면, Then 평균 별점 4.7과 리뷰 수 3이 표시된다.
- Given 리뷰가 모두 삭제된 가게에, When 상세 페이지에 접속하면, Then 평균 별점 대신 "아직 리뷰가 없습니다"가 표시된다.

### FR-6: 검색 (Must)

키워드와 필터, 정렬을 조합해 리뷰를 찾는다.

- 키워드는 가게 이름, 리뷰 제목, 본문에서 대소문자 구분 없이 부분 일치로 찾는다.
- 필터: 지역(입력한 문자열이 포함된 가게, 대소문자·공백 차이 무시), 카테고리, 최소 별점. 여러 조건은 AND로 조합한다.
- 정렬: 최신순(기본), 별점 높은순.
- 검색 조건은 URL 쿼리 파라미터에 담아, 결과 페이지를 공유하거나 뒤로 가기를 해도 같은 결과가 보이게 한다.

**인수 조건**
- Given 본문에 "칼국수"가 들어간 리뷰가 있을 때, When "칼국수"로 검색하면, Then 해당 리뷰가 결과에 포함된다.
- Given 키워드 "국밥", 지역 "종로", 카테고리 "한식"을 지정했을 때, When 검색하면, Then 지역에 "종로"가 포함되고 세 조건을 모두 만족하는 리뷰만 표시된다.
- Given 조건에 맞는 리뷰가 없을 때, When 검색하면, Then "검색 결과가 없습니다" 안내와 검색 조건 초기화 링크가 표시된다.
- Given 검색 결과 URL을 복사해, When 새 창에서 열면, Then 같은 조건과 결과가 표시된다.

### FR-7: 댓글 (Must)

로그인 없이 닉네임, 비밀번호, 내용으로 리뷰에 댓글을 단다.

- 닉네임 2~20자, 비밀번호 4~20자, 내용 1~500자.
- 댓글은 작성순(오래된 순)으로 표시하며, 대댓글은 지원하지 않는다.
- 비밀번호가 일치하면 삭제할 수 있다. 첫 버전에서는 댓글 수정을 지원하지 않는다.

**인수 조건**
- Given 올바른 입력으로, When 댓글을 등록하면, Then 같은 상세 페이지로 돌아오고 새 댓글이 목록 맨 아래에 보인다.
- Given 틀린 비밀번호로, When 댓글 삭제를 요청하면, Then 삭제되지 않고 오류 메시지가 표시된다.
- Given 댓글 내용에 `<script>` 태그가 있을 때, When 상세 페이지를 열면, Then 태그가 실행되지 않고 글자 그대로 보인다.

## 7. 비기능 요구사항

- **성능**: 목록·검색·상세 페이지 서버 응답 p95 500ms 이내 (리뷰 10만 건, 댓글 50만 건 기준).
- **보안**
  - 사용자 입력은 모두 HTML 이스케이프해서 출력한다 (XSS 방지).
  - 쓰기 요청(POST)은 CSRF 토큰으로 보호한다.
  - 비밀번호는 BCrypt 단방향 해시로 저장하고, 로그나 화면에 노출하지 않는다.
  - 모든 페이지는 로그인 없이 접근할 수 있으며, 권한 확인은 리뷰·댓글 비밀번호 대조로만 한다.
  - 요청 횟수 제한은 두지 않는다.
- **환경**: 운영 DB 접속 정보는 코드에 넣지 않고 환경 변수로 주입하며, SSL로 연결한다.
- **SEO**: 페이지마다 고유한 `<title>`과 `<meta name="description">`을 두고, 리뷰 상세는 고정 URL(`/reviews/{id}`)을 쓴다.
- **호환성**: 최신 Chrome, Safari, Edge, Firefox와 모바일 브라우저(너비 360px 이상)를 지원한다.
- **접근성**: 모든 입력 필드에 label을 연결하고, 별점은 숫자 텍스트로도 제공한다.

## 8. 화면 및 흐름

| 화면 | URL | 설명 |
|---|---|---|
| 홈 / 리뷰 목록 | `GET /`, `GET /reviews` | 최신 리뷰 목록과 검색창 |
| 검색 결과 | `GET /reviews?keyword=&region=&category=&minRating=&sort=&page=` | 목록 화면에 검색 조건 적용 |
| 리뷰 작성 | `GET /reviews/new`, `POST /reviews` | 가게 찾기/새 가게 입력 + 리뷰 입력 |
| 리뷰 상세 | `GET /reviews/{id}` | 본문, 가게 정보, 댓글 목록과 댓글 작성 폼 |
| 리뷰 수정 | `GET /reviews/{id}/edit`, `POST /reviews/{id}/edit` | 비밀번호 확인 후 수정 |
| 리뷰 삭제 | `POST /reviews/{id}/delete` | 비밀번호 확인 후 삭제 |
| 댓글 작성·삭제 | `POST /reviews/{id}/comments`, `POST /comments/{id}/delete` | 처리 후 리뷰 상세로 이동 |
| 가게 상세 | `GET /stores/{id}` | 가게 정보, 평균 별점, 리뷰 목록 |

**주요 흐름**
1. 리뷰 작성: 홈 → 작성 버튼 → 가게 찾기(없으면 새로 입력) → 리뷰 입력 → 등록 → 리뷰 상세
2. 리뷰 찾기: 홈 → 키워드·필터 입력 → 검색 결과 → 리뷰 상세 → 가게 상세
3. 댓글: 리뷰 상세 → 댓글 입력 → 등록 → 같은 리뷰 상세

쓰기 요청이 끝나면 모두 리다이렉트해서(PRG 패턴) 새로고침해도 다시 제출되지 않게 한다.

## 9. 기술 고려사항

- **기술 스택**: 현재 프로젝트 구성(Spring Boot 4.1, Java 17, Spring MVC, Thymeleaf, Lombok)에 Spring Data JPA와 Spring Security를 추가한다.
- **DB 환경**
  - 로컬 개발·테스트: H2 인메모리 DB를 PostgreSQL 호환 모드(`MODE=PostgreSQL`)로 쓴다.
  - 배포: Neon의 서버리스 PostgreSQL을 쓴다. 접속 정보는 환경 변수로 받고 `sslmode=require`로 연결한다.
  - 프로필(`local`, `test`, `prod`)로 DB 설정을 나누고, 로컬 기본 프로필은 `local`로 둔다.
  - 로컬 H2 데이터는 재시작하면 사라지므로, 필요하면 개발용 샘플 데이터를 넣는 방법을 둔다.
  - H2와 PostgreSQL의 차이(`pg_trgm` 확장, 인덱스 문법 등)로 테스트가 운영 동작을 완전히 보장하지 못한다. PostgreSQL 전용 구문은 운영 마이그레이션에만 두고, 테스트는 기능 동작 검증에 집중한다.
- **Neon 연결**: Neon은 유휴 시 컴퓨트가 중단되어 첫 요청이 느려질 수 있다. 커넥션 풀(HikariCP) 크기와 타임아웃을 Neon 연결 한도에 맞추고, 필요하면 Neon의 pooled 연결 주소를 쓴다.
- **도메인 모델**
  - `Store`: 이름, 주소, 지역(자유 입력 문자열), 카테고리. (이름, 주소)에 유니크 제약을 둔다.
  - `Review`: Store 참조, 닉네임, 비밀번호 해시, 제목, 본문, 별점, 작성·수정 시각.
  - `Comment`: Review 참조, 닉네임, 비밀번호 해시, 내용, 작성 시각.
- **계층 구조**: Controller(요청 처리와 화면 선택) → Service(비밀번호 확인, 가게 중복 처리 등 업무 규칙) → Repository(JPA). 입력 폼과 엔티티를 분리하고, 입력 검증은 Bean Validation으로 한다.
- **삭제 방식**: 리뷰와 댓글은 DB에서 실제로 지우는 하드 삭제를 쓴다. 리뷰를 지우면 그 리뷰의 댓글도 함께 지운다. 리뷰가 모두 지워진 가게는 남겨 둔다.
- **검색**: 첫 버전은 PostgreSQL의 대소문자 무시 부분 일치(`ILIKE`)와 동적 조건 조합으로 구현하고, `pg_trgm` 인덱스로 성능 목표를 맞춘다. 데이터가 늘면 전문 검색(Full-Text Search) 전환을 검토한다.
- **평균 별점**: 처음에는 조회할 때 집계한다. 성능 목표를 넘기면 Store에 평균과 리뷰 수를 저장하는 방식을 검토한다.
- **보안 구성 (Spring Security)**
  - 회원 인증은 쓰지 않으므로 모든 URL을 `permitAll`로 열고, 기본 로그인 폼과 HTTP Basic은 끈다.
  - CSRF 보호는 켜 두고, Thymeleaf 폼에 CSRF 토큰이 자동으로 들어가게 한다.
  - 리뷰·댓글 비밀번호는 `PasswordEncoder`(BCrypt)로 해시하고 대조한다.
  - 보안 헤더(XSS 방지, 클릭재킹 방지 등)는 Spring Security 기본값을 쓴다.
- **스키마 관리**: 운영 DB 스키마 변경 이력은 마이그레이션 도구(Flyway 등)로 관리한다.

## 10. 위험 요소 및 의존성

- **스팸·도배**: 로그인도 요청 횟수 제한도 없어 광고성 글이나 도배를 막을 장치가 없다. → 첫 버전은 이 위험을 감수하고, 문제가 생기면 요청 횟수 제한, CAPTCHA, 신고 기능을 검토한다.
- **Neon 콜드 스타트**: 유휴 후 첫 요청이 느려 응답 시간 목표(p95 500ms)를 넘길 수 있다. → 측정할 때 콜드 스타트 요청을 따로 보고, 문제가 되면 자동 중단 설정을 조정한다.
- **테스트 DB 차이**: H2와 PostgreSQL의 동작 차이로 테스트는 통과해도 운영에서 실패할 수 있다. → 배포 전에 Neon 개발 브랜치에서 마이그레이션과 검색을 확인한다.
- **비밀번호 분실**: 익명 구조라 비밀번호를 잊으면 글을 고칠 수 없다. → 작성 화면에 안내 문구를 넣고, 삭제 요청 창구는 이후 검토한다.
- **비밀번호 대입 공격**: 비밀번호가 4자부터 가능하고 실패 횟수 제한이 없어, 남의 리뷰를 반복 시도로 지울 수 있다. → 첫 버전은 감수하고, 피해가 생기면 실패 횟수 제한이나 최소 길이 상향을 검토한다.
- **삭제 복구 불가**: 하드 삭제라 실수나 대입 공격으로 지워진 리뷰를 되살릴 수 없다. → DB 백업(Neon 시점 복구)으로만 대응한다.
- **지역 표기 불일치**: 지역을 직접 입력하므로 "서울 종로구", "종로", "서울시 종로구"처럼 표기가 제각각이 된다. → 부분 일치 검색으로 완화하고, 필요하면 이후 지역 목록 선택 방식으로 바꾼다.
- **가게 중복**: 같은 가게가 주소 표기만 달라 여러 번 등록될 수 있다. → 첫 버전은 가게 찾기로 기존 가게 선택을 유도하고, 주소 정규화는 이후 검토한다.
- **명예훼손·허위 리뷰**: 관리 기능이 없어 문제 리뷰에 대응하기 어렵다. → 운영자가 직접 DB에서 처리하는 절차를 정해 둔다.
- **의존성**: Neon 프로젝트와 접속 정보 준비.

## 11. 미결 사항

- [x] 요청 횟수 제한 기준 → 두지 않음
- [x] 테스트 DB → H2, 배포 DB → Neon PostgreSQL
- [x] Spring Security 도입 여부 → 도입 (CSRF, BCrypt)
- [x] 로컬 개발 DB → H2
- [x] 지역 기준 데이터 → 목록 없이 사용자가 직접 입력
- [x] 리뷰 삭제 표시 → 흔적 없이 삭제 (하드 삭제)
- [x] 비밀번호 실패 시 잠금 → 첫 버전에서는 두지 않음
