# SRS 작성

이 스킬은 `docs/srs/` 아래에 SRS를 만들고 관리한다.
PRD가 "무엇을, 왜"를 정한다면, SRS는 개발자가 구현하고 테스트할 수 있을 만큼 "무엇을 정확히"를 정한다.
CLAUDE.md 원칙에 따라 SRS는 설계 문서일 뿐이며, 이 스킬로 코드를 구현하지 않는다.

## 저장 규칙

- 경로: `docs/srs/SRS-<번호>-<kebab-case-영문-슬러그>.md`
- 번호와 슬러그: 원본 PRD와 같게 한다 (예: `PRD-001-restaurant-review-site.md` → `SRS-001-restaurant-review-site.md`).
- 원본 PRD 하나에 SRS 하나를 둔다. PRD가 없으면 SRS를 만들지 말고 `prd` 스킬로 PRD부터 작성하자고 안내한다.
- 색인: `docs/srs/README.md`의 표에 SRS를 한 줄씩 등록하고, 상태가 바뀌면 함께 갱신한다.
- 템플릿: [template.md](template.md)의 구조를 그대로 따른다.
- 상태: `Draft` → `Review` → `Approved`, 폐기되면 `Deprecated`. 파일은 지우지 않고 상태만 바꾼다.

## 작업 절차

1. **원본 PRD 확인**: `docs/prd/`에서 대상 PRD를 읽는다. 상태가 `Approved`가 아니면 그대로 진행할지 사용자에게 묻는다.
2. **기존 SRS 확인**: 같은 번호의 SRS가 있으면 새로 만들지 않고 그 문서를 수정한다.
3. **코드베이스 파악**: 빌드 설정, 패키지 구조, 설정 파일을 읽어 기술 스택과 제약을 실제 코드에 맞게 쓴다.
4. **요구사항 분해**: PRD의 각 `FR-n`과 비기능 요구사항을 검증 가능한 단위의 SRS 요구사항으로 쪼갠다.
5. **질문**: PRD와 코드로 정할 수 없는 세부 값(오류 메시지, 경계값, 정렬 기준 등)만 AskUserQuestion으로 한 번에 묻는다. 답이 없으면 합리적인 기본값을 쓰고 보고할 때 밝힌다.
6. **작성**: 템플릿을 채우고, 추적 매트릭스로 PRD의 모든 요구사항이 빠짐없이 연결됐는지 확인한다.
7. **색인 갱신**: `docs/srs/README.md` 표에 추가하거나 수정한다.
8. **보고**: 파일 경로, 요구사항 수, 임의로 정한 값, 미결 사항을 사용자에게 알린다.

## 요구사항 작성 규칙

- ID 체계
  - `REQ-FUNC-001`: 기능 요구사항
  - `REQ-NF-001`: 비기능 요구사항 (성능, 보안, 호환성 등)
  - `REQ-IF-001`: 외부 인터페이스 (화면, HTTP 엔드포인트, 외부 시스템)
  - `REQ-DATA-001`: 데이터 요구사항 (엔티티, 제약, 보존)
- 요구사항 하나에는 조건 하나만 담고, "~해야 한다"로 끝맺는다.
- 각 요구사항에 출처(PRD의 `FR-n` 등), 우선순위(`Must` / `Should` / `Could`), 검증 방법(`Test` / `Inspection` / `Demonstration` / `Analysis`)을 적는다.
- 입력값은 타입, 필수 여부, 길이·범위, 오류 시 동작까지 표로 명시한다.
- 정상 흐름뿐 아니라 예외 흐름(검증 실패, 대상 없음, 권한 불일치)을 반드시 적는다.
- "적절히", "빠르게" 같은 모호한 표현을 쓰지 않는다.
- 클래스, 메서드 수준의 구현 설계와 코드는 쓰지 않는다. 엔드포인트, 데이터 항목, 상태 코드처럼 외부에서 관찰 가능한 수준까지만 정한다.

## PRD와의 동기화

- 원본 PRD가 바뀌면 SRS도 갱신하고, 두 문서의 `변경 이력`에 서로의 변경을 적는다.
- PRD에 없는 요구사항을 SRS에서 새로 만들지 않는다. 필요하면 PRD 수정을 먼저 제안한다.
- 작성 중 되돌리기 어려운 기술 결정(DB, 배포, 보안 방식 등)이 나오면 `adr` 스킬로 ADR을 남기자고 제안한다.
