# PRD 작성

이 스킬은 `docs/prd/` 아래에 PRD를 만들고 관리한다.
CLAUDE.md 원칙에 따라 PRD는 설계 문서일 뿐이며, 이 스킬로 코드를 구현하지 않는다.

## 저장 규칙

- 경로: `docs/prd/PRD-<번호>-<kebab-case-영문-슬러그>.md` (예: `docs/prd/PRD-001-review-posting.md`)
- 번호: `docs/prd/`의 기존 PRD 중 가장 큰 번호 + 1, 세 자리로 채운다. 번호는 재사용하지 않는다.
- 색인: `docs/prd/README.md`의 표에 PRD를 한 줄씩 등록하고, 상태가 바뀌면 함께 갱신한다.
- 템플릿: [template.md](template.md)의 구조를 그대로 따른다.
- 상태: `Draft` → `Review` → `Approved`, 폐기되면 `Deprecated`. 파일은 지우지 않고 상태만 바꾼다.

## 작업 절차

1. **기존 문서 확인**: `docs/prd/README.md`와 관련 PRD를 읽고, 겹치는 문서가 있으면 새로 만들지 말고 그 문서를 수정할지 묻는다.
2. **요구사항 수집**: 아래 항목 중 요청에서 알 수 없는 것만 AskUserQuestion으로 한 번에 묻는다.
   - 해결하려는 문제와 대상 사용자
   - 성공 지표 (측정 가능한 값)
   - 반드시 포함할 범위와 이번에 제외할 범위
   - 일정·기술 제약
3. **코드베이스 파악**: 현재 구조(Spring Boot, Thymeleaf 등)를 확인해 기술 고려사항을 실제 코드에 맞게 쓴다.
4. **작성**: 템플릿을 채운다. 확인되지 않은 내용은 지어내지 말고 `미결 사항`에 질문으로 남긴다.
5. **색인 갱신**: `docs/prd/README.md` 표에 추가하거나 수정한다.
6. **보고**: 파일 경로, 핵심 요구사항 요약, 미결 사항을 사용자에게 알린다.

## 작성 원칙

- 요구사항은 "무엇을, 왜"에 집중하고 "어떻게 구현하는지"는 기술 고려사항에 방향만 적는다.
- 기능 요구사항마다 ID(`FR-1`, `FR-2` …)와 우선순위(`Must` / `Should` / `Could`)를 붙인다.
- 각 기능 요구사항에는 검증 가능한 인수 조건을 Given / When / Then 형식으로 적는다.
- "빠르게", "편리하게" 같은 모호한 표현 대신 수치나 관찰 가능한 조건을 쓴다.
- 기존 PRD를 수정하면 문서 하단 `변경 이력`에 날짜와 변경 내용을 추가한다.
