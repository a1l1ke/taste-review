# ADR 작성

이 스킬은 `docs/adr/` 아래에 ADR을 만들고 관리한다.
ADR은 결정 하나와 그 배경·대안·결과를 짧게 남겨, 나중에 "왜 이렇게 했는지"를 알 수 있게 한다.
CLAUDE.md 원칙에 따라 ADR은 설계 문서일 뿐이며, 이 스킬로 코드를 구현하지 않는다.

## 저장 규칙

- 경로: `docs/adr/ADR-<번호>-<kebab-case-영문-슬러그>.md` (예: `docs/adr/ADR-001-use-ssr-with-thymeleaf.md`)
- 번호: `docs/adr/`의 기존 ADR 중 가장 큰 번호 + 1, 세 자리로 채운다. PRD·SRS 번호와는 별개이며 재사용하지 않는다.
- 슬러그: 결정 내용을 동사로 시작해 쓴다 (예: `use-neon-postgresql`, `hard-delete-reviews`).
- ADR 하나에는 결정 하나만 담는다. 여러 결정이면 ADR을 나눈다.
- 색인: `docs/adr/README.md`의 표에 ADR을 한 줄씩 등록하고, 상태가 바뀌면 함께 갱신한다.
- 템플릿: [template.md](template.md)의 구조를 그대로 따른다.

## 상태와 변경 규칙

- 상태: `Proposed` → `Accepted` 또는 `Rejected`. 이후 `Deprecated`나 `Superseded by ADR-<번호>`가 될 수 있다.
- `Accepted`된 ADR의 결정 내용은 고치지 않는다. 결정이 바뀌면 새 ADR을 만들고, 기존 ADR의 상태를 `Superseded by ADR-<새 번호>`로, 새 ADR의 `대체하는 ADR`에 기존 번호를 적는다.
- 오타, 링크 수정처럼 결정과 무관한 수정만 기존 ADR에 직접 반영하고 `변경 이력`에 남긴다.
- 파일은 지우지 않는다.

## 작업 절차

1. **기존 ADR 확인**: `docs/adr/README.md`를 읽고, 같은 주제의 ADR이 있으면 새 ADR로 대체할지 사용자에게 묻는다.
2. **맥락 수집**: 관련 PRD·SRS(`docs/prd`, `docs/srs`)와 코드(빌드 설정, 설정 파일)를 읽어 결정의 배경과 제약을 확인한다.
3. **질문**: 결정 내용, 검토한 대안, 선택 이유 중 문서와 대화로 알 수 없는 것만 AskUserQuestion으로 한 번에 묻는다.
4. **작성**: 템플릿을 채운다. 사용자가 정하지 않은 결정은 `Proposed`로 두고, 사용자가 확정한 결정만 `Accepted`로 쓴다.
5. **연결**: 관련 PRD·SRS가 있으면 ADR의 `관련 문서`에 링크한다.
6. **색인 갱신**: `docs/adr/README.md` 표에 추가하거나 수정한다.
7. **보고**: 파일 경로, 결정 요약, 상태, 확인이 필요한 점을 사용자에게 알린다.

## 작성 원칙

- 결정은 "우리는 ~한다" 형태의 한두 문장으로 분명하게 쓴다.
- 대안은 실제로 검토할 만한 것을 2개 이상 적고, 각각 장단점과 채택하지 않은 이유를 적는다.
- 결과에는 좋은 점뿐 아니라 감수하는 단점과 이후 해야 할 일도 적는다.
- 문서 전체는 한 화면에서 읽을 수 있을 만큼 짧게 유지한다. 상세 요구사항은 SRS에, 제품 목표는 PRD에 둔다.
- 코드는 쓰지 않는다. 필요하면 설정 키나 라이브러리 이름 정도만 적는다.
